# n_discarded: скользящее окно контекста вместо пересборки

Базлайн, к которому вернулись: `MERIDIAN_CHAT_ENGINE=sdk` (дефолт), layout
`current`, k=5. Движок `direct` из docs/todo-5.md остаётся, но выключен.

Задача: проверить `modelConfig.n_discarded` — вариант «выкинуть (q1, a1) и
оставить остальное в KV» вместо компакции с полным prefill.

## Что это вообще такое

Одна строка в README аддона (`@qvac/llm-llamacpp@0.45.0`):

> `n_discarded` | integer | 0 | Tokens to discard in sliding window context.

Плюс поле в публичной Zod-схеме SDK (`modelConfig.n_discarded`). Больше
документации нет. Поэтому сначала прямой замер на аддоне, потом продукт.

## Замер на аддоне

`evals/exp/kv-discard/probe-discard.mjs` — Qwen3.5-0.8B, `ctx_size` 1024,
системный промпт с секретом `ZULU-7`, дальше по одному факту на ход
(«склад в Лиссабоне держит 412 паллет»), каждый ход ~170 токенов, всё на
одной живой последовательности. В конце три вопроса: секрет из системного
промпта, самый старый факт, самый свежий.

    n_discarded=0                              n_discarded=256
    prime          cache 33                    prime          cache 33
    fill Lisbon    cache 203                   fill Lisbon    cache 203
    ...                                        ...
    fill Perth     cache 884                   fill Perth     cache 884
    fill Riga      ERROR context overflow      fill Riga      cache 799   <- сдвиг
                   at batch prefill step       fill Tunis     cache 969
                   (1055 tokens, max 1024)     fill Hanoi     cache 884   <- сдвиг

    Q секрет       -> 1234  (состояние снесено) Q секрет      -> ZULU-7
    Q старый факт  -> 10                        Q старый факт -> 271  (это Perth, не Lisbon)
    Q свежий факт  -> 10                        Q свежий факт -> 847  (верно)

Выводы, все подтверждены замером:

1. **Работает.** Выключенным (`0`) ход, который пересекает `ctx_size`, падает
   с `context overflow at batch prefill step`, и живая последовательность
   теряется целиком. Включённым аддон выбрасывает ровно `n_discarded` токенов
   с начала окна (884 + 170 − 255 = 799) и продолжает.
2. **Системный промпт защищён.** 32 хода, ~14 сдвигов подряд (`ctx 1024`,
   `n_discarded 256`, 4 круга фактов) — `ZULU-7` отвечается верно до конца.
   Окно открывается сразу за праймленным префиксом. Это же пишет и сам SDK:
   «the addon's discard window opens at the end of the primed prefix — which
   is where the tool block sits, since the prime is the system prompt alone —
   and nothing protects it» (`completion-stream.js:211`), поэтому при
   `n_discarded > 0` SDK шлёт блок тулов заново каждый ход.
3. **Старое теряется молча.** На вопрос про вытесненный Лиссабон модель не
   говорит «не знаю», а уверенно отдаёт число соседнего склада.
4. Режет **по токенам, а не по сообщениям**: «выкинуть именно (q1, a1)»
   заказать нельзя, можно только «выкинуть N токенов с начала».

## Что пришлось починить, чтобы это заработало в продукте

Две вещи вылезли на первом же живом прогоне (`ctx 6144`, layout `all`).

**1. Скользящее окно и компактор ризонинга несовместимы.**

    [TextLlm] ReasoningBlockCompactor::compact: generation-time context slide
    invalidated tracked reasoning state (pos=6144, discarded=1536, seqId=0)

`remove_thinking_from_context` для семейства Qwen3 включён по умолчанию: он
вырезает `<think>…</think>` из KV в конце генерации через `seq_rm + seq_add`.
Если сдвиг окна происходит *во время* генерации, отслеживаемые позиции
ризонинга уезжают, и по контракту аддона это hard-fail, а не тихая деградация.
Окно — это то, что держит контекст в границах, поэтому уступает компактор:
при `chatDiscard > 0` в `generationParams` идёт
`remove_thinking_from_context: false`.

**2. `generationParams` вызывающего затирал наши дефолты.**

`src/chat/answer.js` собирал `generationParams: { temp: 0.2, predict: 320,
...params.generationParams }`, а следом в тот же объект разворачивал
`...params` — а `params` содержит `generationParams`. Итог: до SDK доезжал
пустой `{}`. Ни `temp`, ни `predict`, ни новый флаг окна.

Отсюда и старое наблюдение «SDK не соблюдает predict»: он его просто никогда
не получал (медиана генерации 380 при `predict: 320`, максимум 11853).
Починено: `generationParams` вынут из остаточного спреда, бюджет генерации
поднят до 4096 (`MERIDIAN_CHAT_PREDICT`) — на 320 с включённым ризонингом
резались бы почти все ответы.

**3. Окно не спасает, когда один промпт больше всего контекста.**

    [TextLlm] context overflow at batch prefill step: prompt tokens 8793,
    max context tokens 6144

Сдвиг работает только между ходами, по живому кэшу. Если кэш потерян и
история реплеится целиком, батч сам по себе больше `ctx_size` — и это по-
прежнему отказ. Поэтому `ctx_size` обязан покрывать самый большой одиночный
промпт: у layout `all` с k=5 это до 10.5k токенов. `ctx 6144` не годится,
`8192` уже держит.

## Новые ручки

| env | что делает |
|---|---|
| `MERIDIAN_CHAT_DISCARD` | `modelConfig.n_discarded` роли chat; 0 = выключено |
| `MERIDIAN_CHAT_CTX` | переопределяет `ctx_size` тира для роли chat |
| `MERIDIAN_CHAT_PREDICT` | бюджет генерации хода на SDK-пути (4096) |

### Сколько раз окно сработало

Считается по тождеству `cached(t) = cached(t-1) + prefill(t) + gen(t) −
удалённое` (`cacheTokens` у SDK — это размер живого KV на конец хода, не
«подано из кэша»; тождество сходится до токена). Сдвиг снимает точное кратное
`n_discarded`, компактор ризонинга — произвольный `<think>`-спан.

    discard-all-8k   26 сдвигов ровно по 2048, 53248 токенов всего,
                     первый сдвиг медиана на 5-м ходу, в 8 сессиях из 9,
                     пик живого KV 8116 из 8192
    all-8k-nodiscard 0 сдвигов, пик живого KV ровно 8192 — упор в потолок

### Что показал контроль

Без окна отказ выглядит так: живой KV доходит до `ctx_size`, генерация
обрезается границей контекста, ход откатывается, следующий ход реплеит всю
историю целиком — и если реплей больше окна, это HTTP 500. **5 таких ошибок
на 83 хода** против 1 у окна (и та единственная — тот же реплей больше
`ctx_size`, от которого сдвиг не спасает).

Разбор одной сессии (`multiquery-02`), живой KV / prefill / генерация:

    окно ВКЛ                          окно ВЫКЛ
     4  7514  2043   376               10  6178    21   133
     5  6292   455   371  ✂ −2048      11  8192    24  1989  ← потолок,
     6  7274   461   521                                 генерация обрезана
     7  7735   461  4096  ✂ −4096      12  5796  5539   519  ← полный реплей
     8  6299  5676   466  откат            (дальше t14: HTTP 500)

### Цена по качеству

Разбил ходы `discard-all-8k` на «до первого сдвига в сессии» и «после» и
сравнил с baseline на тех же самых ходах:

| | n | grounded | false abstain |
|---|---|---|---|
| discard, до сдвига | 29 | 100% | 15% |
| discard, после сдвига | 53 | 98% | 7% |
| baseline, те же 53 хода | 53 | 98% | 7% |

**Измеримого падения после вытеснения нет.** Но это свойство задачи, а не
окна: здесь RAG подтягивает врезки заново каждый ход, поэтому вытесняется в
основном то, что и так продублировано. Место, где окно ломается, видно только
в пробе, где факт живёт исключительно в истории: вытесненный факт → уверенный
неправильный ответ, «не знаю» не звучит ни разу.

### Вывод

`n_discarded` работает и делает ровно то, что обещает. На этой задаче он:

- убирает 4 из 5 отказов по переполнению;
- держит живой KV на полке вместо роста до потолка;
- даёт cache ratio 74% и prefill на сессию 10.7k против 29.3k у baseline;
- режет TTFT p95 с 5553 до 2327 мс и стену p95 с 15775 до 10468 мс.

Чего он не делает: не спасает от одиночного промпта больше `ctx_size`
(1 ошибка осталась), не режет по границам сообщений и **не сообщает
приложению, что что-то потеряно**. Последнее — причина, по которой это не
дефолт ни у одного провайдера: режим отказа не «стало хуже», а уверенный
неправильный ответ без единого сигнала.

Побочно: `all-8k-nodiscard` утекает `</think>` в видимый ответ на 20 ходах из
83, а `discard-all-8k` — ни на одном. Разница в том, что при включённом окне
компактор ризонинга выключен, и состояние KV остаётся согласованным с тем,
что модель сама сгенерировала. Компактор под layout `all` оставляет в кэше
ответы без их `<think>`, и модель начинает дописывать лишний закрывающий тег.

## Поправка в учёте токенов (2026-09-21)

`cacheTokens` у аддона документирован как «Final cache tokens» — размер
**живого KV на конец** вызова, в него уже входят и префилл этого хода, и
сгенерированное. `src/chat/stats.js` складывал его с `promptTokens`, то есть
считал собственный промпт и ответ хода дважды. Видно было сразу: на первом
ходу сессии, где переиспользовать нечего, `prompt` выходил 6073 при
`prefill` 2579, а `context_tokens` поднимался выше `ctx_size` — физически
невозможное число.

Правильно:

    переиспользовано = cacheTokens - promptTokens - generatedTokens
    живой контекст   = cacheTokens   (без ключа кэша: prefill + генерация)

Починено в `src/chat/stats.js` (+2 теста) и в строках эвала
(`evals/run.mjs`). Прогоны пересчитаны из сохранённых трейсов скриптом
`evals/exp/kv-discard/recount.mjs` — сырые постраундовые stats там есть, так
что перепрогон не понадобился. Что поехало:

| | было | стало |
|---|---|---|
| discard-all-8k: контекст макс | 11975 | 8116 |
| all-8k-nodiscard: контекст макс | 15543 | 8192 |
| discard-all-8k: cache ratio | 83.7% | 74.1% |
| discard-all-8k: токенов на сессию | 71237 | 56449 |
| context-all-k5: контекст макс | 21276 | 16384 |

`prefill`, recall, латентность и счётчики ошибок не менялись — они считались
из других полей.

Отдельно: движок `direct` отдавал `cacheTokens` в другом смысле (свой
чекпоинт до хода, потому что живой размер врёт при откате по `predict`).
Теперь его клиент приводит поле к смыслу аддона, и правило одно на оба пути.

## Тулы в системном промпте (MERIDIAN_TOOLS_IN_SYSTEM=1)

При включённом окне блок тулов нельзя кэшировать (`toolBlockEvictable`), и
SDK шлёт его каждый ход — замерено 439 токенов на тёплом ходу. Системный
промпт праймится и защищён `n_keep`, так что перенос блока туда снимает эту
плату. Реализовано: `renderToolBlock()` в `src/chat/tools.js`, флаг в
`src/config.js`, разбор вызовов своим `parseToolMarkup`, потоковый фильтр
`createMarkupFilter` (иначе разметка уходит в SSE мимо `stripToolMarkup`).

Выигрыш подтверждён — тёплый ход с окном:

    блок в tools SDK        prefill 459
    блок в системном        prefill  15

Цена, категория `tools`, 11 кейсов тира M:

| | baseline | tools-in-system |
|---|---|---|
| routing tp / fn | 2 / 5 | 1 / 6 |
| precision | 100% | 100% |
| args subset | 50% | 100% |
| must | 54.5% | 54.5% |
| утечка разметки | 0% | 0% |
| **пустых ответов** | **9%** | **36%** |
| генерация на ход | 747 | 1368 |

Пустые — это разгон ризонинга: 3 хода из 11 (против 1 у baseline) съедают
весь `predict` 4096 на `<think>` (14–19 тысяч символов) и не закрывают блок.
Тот же отказ, что и **вовсе без** объявленных тулов, только реже: блок в
системном промпте стоит не в той позиции, на которую модель обучена (Qwen3.5
привязывает его к последнему user-сообщению), и дисциплина формата падает.
Ограничить это нечем: `reasoning_budget 0` ломает вызовы тулов, а
положительное значение аддон не соблюдает.

Вывод: механизм рабочий, по умолчанию выключен. Включать имеет смысл только
вместе с окном и только если разгон ризонинга удастся прижать.
