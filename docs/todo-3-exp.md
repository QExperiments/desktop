## Оси эксперимента и варианты

Одна ось за раз от базы **B0** (как в проде), потом один сборный вариант из победителей. Каждый вариант
= отдельная LanceDB-директория (`data/lancedb-exp/<variant>`), заново проиндексированная тем же
`ingest()` с переопределениями через env. Всего 15 вариантов + сборный.

| # | Ось | Вариант | Что меняется | Ожидание |
| --- | --- | --- | --- | --- |
| B0 | база | `embeddinggemma-300M-Q8_0`, 768 dims, chunk 512/64 paragraph+token, без префиксов, RRF k=60 cosine+BM25 (stem, stop-words, lowercase, ascii) | — | recall@3 83 %, MRR 0.91 (прогон 2026-09-20) |

| E3 | embedding-модель | `GTE_LARGE_FP16` (335M, 1024 dims, 670 MB, ctx 512) | другая архитектура, без task-префиксов | другой профиль ошибок; чанк должен быть ≤ 512 токенов |
| C1 | чанкинг | chunkSize 256, overlap 32 | ~70 чанков | precision@1–3 выше, 2–3-gold запросы могут просесть (чанки одного файла вытесняют другие) |

| P1 | подготовка | task-префиксы EmbeddingGemma: документ `title: <file> \| text: …`, запрос `task: search result \| query: …` | модель обучена с ними, сейчас не используются | +2…5 pp на paraphrase-запросах |
| P2 | подготовка | заголовок чанка: `file: emails/007-sla-reminder.md · type: emails · <subject/первая строка>` перед текстом (и в embed, и в FTS) | контекст файла в каждом чанке | + на follow-up/paraphrase, + на «которое письмо» |
| P3 | подготовка | CSV → чанк на строку (`sku=…, list_price_usd=…`), JSON → чанк на запись верхнего уровня | сейчас key=value-строки склеены и режутся по токенам | Atlas health score (сейчас ранг 8), SKU-запросы |
| P4 | подготовка | MRL-усечение вектора 768 → 256 (renormalize) | индекс в 3 раза меньше, поиск быстрее | −0…2 pp; проверка, стоит ли экономить |
| F1 | слияние | RRF по top-10 с каждого плеча, потом срез до k | сейчас fuse top-k ∪ top-k | Q2-отчёт (bm25 ставит 1-м, RRF 4-м) должен подняться |
| F2 | слияние | вес BM25-плеча 1.5 в RRF (или k_rrf 20 вместо 60) | сильнее точные термины | + на keyword/identifier, риск на paraphrase |
| F3 | FTS | `stem: false, removeStopWords: false` | идентификаторы и коды без стемминга | `REC-SE-2026-0626`, `CL-PDM-SITE` |
| F4 | FTS | `baseTokenizer: 'ngram'` (3-грамма) для BM25-плеча | частичные совпадения кодов, опечатки | + на identifier, шум на длинных |
| BEST | сборный | лучшие по осям E / C / P / F вместе | проверка аддитивности | ≥ max по осям, иначе есть конфликт |

Не входит: Qwen3-Embedding-0.6B из реестра (addon `audiogen`, не `embeddings` — `embed()` его не грузит),
reranker (нет модели в SDK), sentence-split (в SDK 0.18.2 не режет).

## Метрики

Качество (по 133 запросам, каждая для k = 1, 3, 4, 5, 7, 10):
- **recall@k** — доля gold-файлов среди top-k чанков; главная.
- **precision@k** — доля top-k чанков из gold-файлов; показывает шум, который увидит модель.
- **MRR** — где первый gold; чувствительнее recall@1 при малом n.
- **hit@k** — хотя бы один gold в top-k (уже есть, ничего не стоит).
- Срезы recall@3: по источнику/стилю запроса и по типу gold-файла. Парное сравнение с B0: сколько
  запросов стало лучше / хуже (Δ recall@3 < 4 pp при n = 133 — шум, SE ≈ 3.3 pp).
- 4 канарейки, ранг gold в каждом варианте (сейчас, B0): `retrieval-36` «total recognized revenue in
  Q2 2026» — Q2-отчёт ранг 3, transcript ранг 6 (в чате при k = 3 отчёт был 4-м); `retrieval-129` Atlas
  health score — JSON ранг 8; `retrieval-120` `REC-SE-2026-0626` — ранг 6; `retrieval-07` hiring plan —
  transcript field-ops вне топ-10.

Цена (на вариант):
- чанков в индексе, байт на диске (`data/lancedb-exp/<v>`), размер embedding-модели;
- ingest: время, embed-токенов всего и tok/s (из `embed().stats`);
- запрос: retrieval_ms p50/p95 (embed запроса + поиск), отдельно embed запроса и LanceDB.

## Batch-запросы к embedding-модели ([I.2] для embed-пути)

Скрипт `evals/embed-batch.mjs`, модель B0, тексты = 34 чанка и 133 запроса, три режима:
1. **sequential** — `embed({ text })` по одному, await каждого;
2. **array** — один `embed({ text: [...] })` (то, что делает ingest сейчас);
3. **concurrent** — N одиночных `embed()` через `Promise.all` (проверяем, сериализует ли SDK).

Меряем: wall, тексты/с, tok/s (из `stats`), задержка первого результата; для array — совпадает ли порядок
векторов с порядком входа (сравнить с sequential покоординатно); отмена одного in-flight `embed` по
`requestId` через `cancel()` без влияния на остальные. Повторить при `modelConfig.batchSize` 512 / 1024 /
4096 (сейчас 4096) и на `device: 'cpu'`. Ответ на [I.2.1] в терминах embed: во сколько раз батч быстрее
последовательных вызовов. Для `batchCompletion` (LLM) — тот же скрипт-скелет, отдельный эксперимент.

### Batch-запросы к embedding-модели ([I.2] / [I.2.1] для embed-пути)

`node evals/embed-batch.mjs --batch 1024,4096,512 --cpu`, отчёт `evals/results/embed-batch-2026-09-20/report.md`
(медиана из 3 повторов; 34 чанка ≈ 600 токенов и 133 запроса ≈ 15 токенов; Q8_0, M4 Pro).

| конфиг | набор | sequential | array (один `embed({text:[…]})`) | ускорение | concurrent (`Promise.all`) |
| --- | --- | --- | --- | --- | --- |
| gpu, batchSize 4096 | 133 запроса | 823 мс (6 мс/шт) | 134 мс (1 мс/шт) | **×6.1** | 395/399 отклонены |
| gpu, batchSize 4096 | 34 чанка | 967 мс (28 мс/шт) | 898 мс | ×1.1 | 99/102 отклонены |
| gpu, batchSize 1024 | 133 запроса | 826 мс | 143 мс | ×5.8 | 396/399 отклонены |
| cpu, batchSize 4096 | 133 запроса | 513 мс | 308 мс | ×1.7 | 394/399 отклонены |
| cpu, batchSize 4096 | 34 чанка | 2 881 мс | 2 587 мс | ×1.1 | 99/102 отклонены |
| gpu, batchSize 512 | — | ошибка `batch overflow: 595 tokens exceeds batch size (512)` | | | |

- **Ответ на [I.2.1] для embed:** батч выигрывает там, где доминируют накладные расходы на вызов — короткие
  запросы ×6 на Metal (6 → 1 мс на текст), ×1.7 на CPU. На длинных чанках вычисления доминируют: ×1.1,
  ~14 k tok/s на GPU и ~5 k на CPU в обоих режимах. Ingest по одному вызову на файл (как сейчас) — правильно.
- **Параллельные одиночные вызовы SDK не принимает**: движок держит одну задачу, остальные падают сразу с
  `Cannot set new job: a job is already set or being processed` (97–99 % отклонённых). Значит, на сервере
  запросы к эмбеддеру надо сериализовать или собирать в массив; сейчас `retrieve.search` вызывает `embed`
  по одному и под нагрузкой из нескольких сессий получит эту ошибку — **это надо закрыть очередью**.
- **Порядок в array сохраняется**: косинус вектора i с последовательным вектором i = 1.0000 (0.9996 на CPU),
  с соседом ≤ 0.95.
- **Отмена по `requestId`** работает для array-запроса: `cancel()` через 5 мс → `Job cancelled` за 10–14 мс,
  модель после этого отвечает. Отмена одного из пяти параллельных бессмысленна — они и так отклоняются.
- **`modelConfig.batchSize` — это предел токенов одного входа**, не размер пачки: 512 не вмещает наш чанк
  (ragChunk считает 512 «токенов», модель видит 595). Минимум 1024 при chunkSize 512; сейчас 4096 — ок.
- **CPU-приближение полевого ноутбука**: одиночный запрос 4 мс (быстрее Metal на коротком входе — меньше
  накладных), чанки в 3 раза медленнее GPU (85 мс/чанк). Ingest 34 чанков на CPU ≈ 3 с; загрузка модели
  1123 мс на CPU против ~1 100 на Metal.
- Для `batchCompletion` (LLM) — тот же скелет, отдельный эксперимент; judge-опыт из todo-2 говорит, что на
  Metal батч 4 медленнее одиночных (14.4 против 10.7 с/вердикт).

## Эксперимент 3: раскладка контекста (2026-09-21)

**Вопрос.** Куда класть выдержки: оставлять их в каждом ходе (как было, ADR-011) или держать
только в последнем? Что это даёт по токенам, сколько ходов влезает в ctx тира и чем платим.

**Сначала — баг учёта.** При KV-ключе SDK отдаёт `prompt = cached + prefill`, и на первом вызове
сессии это ровно удвоение: один и тот же первый ход даёт 3519 (KV вкл.) против 1765 (KV выкл.)
при идентичном содержимом; проверено на 9 сессиях (1582→3171, 2195→4428 …). Со второго хода
расхождение рассасывается. Поэтому размер контекста считается не по `prompt_tokens`, а
восстановлением `ctx(t) = ctx(t−1) + completion(t−1) + prefill(t)` (для прогонов без KV
`prompt_tokens` и есть контекст; для хода-компакции — `prefill + системный префикс`).

**Прогоны** (multiquery, 83 хода, tier M, без judge; `evals/results/compare-new-default-2026-09-21/`):
`all k3` (что было), `all k5`, `current k5` (+ запрос из истории, новый дефолт), `budget 8k`.

**Что из этого следует.** При равном k поиск от раскладки не зависит (recall@5 91 % в обеих
раскладках, MRR 0.92) — разрыв 74 против 95 складывается из k=3→5, запроса из истории (follow-up
86 → 94) и семи ходов, которые в `all k3` умерли от переполнения после беглеца на 8777 токенов.
`leak` показывает скрытую цену старой раскладки: 22 % ответов (39 % при k=5) опирались на чанки
прошлых ходов, и «evidence in context 100 %» держалось на них, а не на поиске.

**Почему `current` без KV.** Состояние кэша SDK ключуется сессией, хранит счётчик покрытых
сообщений и только дописывается: переписать или убрать из него раннее сообщение нельзя, можно
лишь удалить файл целиком (`kv-cache-session.js`, `deleteKvCacheState`). Занижение счётчика не
спасает — аддон уже записал выдержки этого хода в состояние. Отсюда `MERIDIAN_CONTEXT_BUDGET`:
пока оценка контекста (с запасом `k × 420` на выдержки самого хода) ниже бюджета, выдержки живут
в кэшированном префиксе и KV переиспользуется как раньше; ход, который бюджет перешагнёт, роняет
файл и один раз проигрывает чистую историю. На 83 ходах бюджет 8k дал 9 компакций: ходы без новых
чанков стоят 15–20 токенов prefill и 37 мс TTFT, компакция — 3.8–4.7k и 2.8–3.4 с.

**Дефолт (ADR-014):** `MERIDIAN_CONTEXT_LAYOUT=current`, `MERIDIAN_CHAT_TOPK=5`,
`QUERY_HISTORY_TURNS=3` + `WHEN=elliptical` (вариант E3 сетки Эксперимента 2: при k=5 он даёт
95 % против 91 % у B0), `MERIDIAN_CONTEXT_BUDGET=0`. Бюджет оставлен знобом: он меняет латентность
в 3.7 раза, но возвращает 17 % leak. Беглецы (`predict` не останавливает генерацию, todo-2) при
k=5 бьют сильнее: wall p95 35 с на одном ходе — это первое, что надо чинить дальше.
